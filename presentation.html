01 · The problem

Coverage isn't the bottleneck — timing is.

~85% of parcels cross the city (median drop ~10–12 km from pickup). A hub almost always exists within 5 km of the drop; the binding question is whether the parcel can physically reach it by 22:00. So the design objective is to minimise transit time, then strip cost via consolidation without losing SDD.

Insight 1

Direct beats central

Routing via one central hub inflates middle-mile distance 2.5–2.75× and adds a second sort — it arrives 77–198 min later. A peer mesh holds SDD at the coverage ceiling.

Insight 2

Mesh is expensive

A van on every O-D pair maxes SDD but runs near-empty (median ~6 parcels/lane). The work is consolidating the thin tail onto fuller trunks — without losing the fat corridors.

Insight 3

Cadence & tiers

Evening-loaded linehauls + mother-hub trunks + an express overlay + on-demand riders recover most of the cost for a few SDD points. The result is the network below.

02 · How the network connects

First mile → sort → mid mile → OFD

Every parcel flows through the same skeleton. The flow service models it exactly with a time-expanded graph: departure/arrival slots are clock-times, lanes carry travel/sort durations, and a fastest-path Dijkstra finds the route.

First mile · warehouse → network

Two tiers by distance to nearest hub

  • Near (<5 km, 537 WH): on-demand 2-wheeler rider, hourly from 11:00 — cheap short hops in dense areas.
  • Far (≥5 km, 47 WH): scheduled van, 2 runs/day (12:00 & 16:00) — outer-city stores with no rider supply.

Realistic first-mile: 6,001 runs/day, rider-dominant.

Mid mile · network → network

Four routing tiers per O-D pair

  • Trunk: mother ↔ mother backbone (full mesh, ≥5 km apart).
  • Spoke: every hub → its nearest mother.
  • Express van: fat corridors (≥50 parcels/day) go direct, evening-loaded.
  • Rider 2-wheeler: short-thin cross-hub lanes (<5 km, ≥5/day) go direct.

Linehaul cadence is asymmetric — noon-start, dense in the SDD-critical evening (12,15,17,19,21).

04 · How costing is done

Three legs, priced like the real fleet

Every served order is routed through the graph; each lane it traverses books a vehicle trip = ceil(parcels on that scheduled departure / capacity). So a near-empty scheduled run still costs one base-priced trip, and an over-full one books a second. Cost-per-order (CPO) = leg cost ÷ orders.

05 · Decision-making, integration & assumptions

Built on the live flow service — not a spreadsheet

Integration

  • Source of truth: Postgres holds hubs (Node), warehouses (WarehouseCluster), slots and lanes.
  • Routing engine: an in-process time-expanded graph (python-igraph) is the read-side cache; a vertex per slot, an edge per lane.
  • Simulation: each order routes WC-{pickup} → nearest hub to drop via the service's fastest-path Dijkstra — the same code that serves the ops API.
  • Decisions are data: mother selection, express/rider eligibility and cadence are explicit, tunable build parameters — the network is reproducible from a CSV + flags.

06 · Simulation results · three days

Performance holds while cost drops with scale

The same post-scale network, simulated on three demand days — light (5.7k), peak (30.9k) and a 50k stress day. SDD stays flat near 91%; total cost-per-order falls from ₹92.80 to ₹64.00 as fixed vehicle costs amortise over fuller loads.
